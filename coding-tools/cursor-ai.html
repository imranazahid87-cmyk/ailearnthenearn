Lesson 01 — Foundations

Cursor, an editor built around AI

Cursor is a full code editor — a fork of VS Code — with AI woven directly into every layer: completions, chat, and multi-file edits, instead of AI bolted on as an extension.

01.1 What makes Cursor different

Because Cursor owns the whole editor, it can do things a plugin can't: index your entire codebase for context, apply changes across several files at once, and let you approve or reject a diff the way you'd review a pull request. It keeps every VS Code shortcut and extension you already know.

It sits closer to "AI-native IDE" than "assistant added to my editor," which is the main trade-off versus lighter tools: more power, but it asks you to actually switch editors.

01.2 Where it fits in your workflow

Codebase-aware chat

Ask questions that reference files you haven't opened; it retrieves relevant context automatically.

Multi-file edits

Describe a change that spans several files and review it as one coherent diff before applying.

Refactoring at scale

Rename, restructure, or migrate patterns across a codebase with the model tracking dependencies.

Daily driver replacement

Works well as your main editor, not just a tool you open occasionally for a specific task.

01.3 The one mindset shift that matters

Review diffs like a reviewer, not an author. Cursor's biggest risk is trusting a multi-file change too quickly — read every file it touched before accepting, the same way you'd review a colleague's pull request.

With that mindset in place, Lesson 2 covers the actual day-to-day routine.

Lesson 02 — Practice

A working edit-and-review routine

How to use Cursor's multi-file power without losing track of what actually changed.

02.1 A five-step routine

  1. 01 Reference specific files or symbols in your prompt so Cursor pulls in the right context first.
  2. 02 Ask for a plan on any change touching more than one file, before letting it write the diff.
  3. 03 Review the diff file by file, not as one block — skimming hides the file where the mistake lives.
  4. 04 Run your test suite immediately after applying a multi-file change, not at the end of the day.
  5. 05 Commit in small chunks so a bad AI edit is easy to isolate and revert.

02.2 A small example

A prompt that gives Cursor enough scope to work safely across files:

Rename the `userId` field to `accountId` across the models,
API routes, and frontend types in this repo. Show me the
full diff before applying, and flag any file you're unsure about.

Naming the scope (models, routes, types) and explicitly asking it to flag uncertainty keeps the change bounded and reviewable.

02.3 Mistakes to avoid

Accepting whole diffs blind

A green "Apply" button is not a substitute for actually reading what changed.

Under-specifying scope

"Fix the bug" with no file or symbol reference forces guesswork across a large codebase.

No test run after apply

Multi-file changes are exactly where a quiet regression is easiest to miss without tests.

Giant, unreviewed commits

Bundling many AI edits into one commit makes rollback painful if something's wrong.

Cursor's power scales with how precisely you scope a request — vague prompts on a large codebase are where it goes wrong most often.
