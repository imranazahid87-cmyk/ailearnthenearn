Lesson 01 — Foundations

GitHub Copilot, the industry default

Copilot is GitHub's AI pair programmer, built into the editors and workflows most developers already use — inline suggestions, chat, and now agentic pull-request-level changes.

01.1 What makes Copilot different

Copilot's edge isn't a single feature, it's reach: it lives inside VS Code, JetBrains, Neovim, and GitHub.com itself, backed directly by the platform that hosts most of the world's code and issues. That means it can reason using real repository context — issues, pull requests, and commit history — not just the open file.

It has also grown from autocomplete into an agent that can open a pull request, work through review comments, and iterate — closer to a teammate than a suggestion box.

01.2 Where it fits in your workflow

Inline completions

Fast, familiar autocomplete tuned on an enormous base of public and private code.

Copilot Chat

Ask questions about your repo, generate tests, or get an explanation without leaving GitHub or your IDE.

PR-level agent tasks

Assign an issue to Copilot and let it open a draft pull request you review like any teammate's.

Team-wide adoption

Enterprise policies, code referencing, and audit tools make it a common default for larger teams.

01.3 The one mindset shift that matters

Treat every Copilot pull request exactly like a human contributor's — read the diff, question the approach, and request changes. Its access to your repo makes it convenient, not automatically correct.

Lesson 02 — Practice

A working review-first routine

How to fold Copilot into a normal GitHub flow without lowering your review bar.

02.1 A five-step routine

  1. 01 Write clear, well-scoped issues — Copilot's agent output is only as good as the issue it's given.
  2. 02 Let inline suggestions handle small, local completions; save agent tasks for well-defined, bounded issues.
  3. 03 Review its pull requests with the same checklist you'd use for a human — tests, edge cases, naming.
  4. 04 Use Copilot Chat to ask "why" before requesting changes, so your feedback targets the real reasoning gap.
  5. 05 Keep CI checks mandatory on Copilot's PRs — never merge on green suggestion alone.

02.2 A small example

An issue description that gives the agent a fair chance to succeed:

Add input validation to the /signup endpoint: reject empty
email/password, return 400 with a clear error message, and
add tests covering both valid and invalid payloads.

It states the endpoint, the exact behaviour, and the expectation of tests — a scoped, checkable unit of work rather than an open-ended ask.

02.3 Mistakes to avoid

Vague issues for the agent

"Improve error handling" with no scope produces a guess, not a targeted fix.

Merging without reading

A passing CI run isn't the same as a human confirming the change does the right thing.

Skipping local testing

Always pull the branch and try it yourself for anything touching user-facing behaviour.

Over-relying on one tool

For deep architectural decisions, use it as one input among several, not the final word.

Copilot is most valuable where GitHub already has the most context — issues, PRs, and CI — so invest in writing those well.
